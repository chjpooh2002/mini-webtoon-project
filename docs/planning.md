# 미니 웹툰 플랫폼 기획 문서

> 작성 시작: 2026-11-18 · 기간: 2026-11-30 ~ 2027-02-21 (12주)
> 이 문서는 프로젝트의 판단 기준이다. 범위가 애매하거나 우선순위가 충돌하면 이 문서로 돌아온다.

## 1. 왜 하는가

### 1.1 한 문장 목표
**"읽기가 몰리는 콘텐츠 서비스를 직접 만들고, 측정에 근거해 병목을 찾아 개선한 경험"을 근거 자료와 함께 설명할 수 있는 상태가 된다.**

### 1.2 얻어갈 경험

각 경험은 "끝났을 때 무엇을 말할 수 있는가"와 "그걸 증명하는 산출물"로 정의한다. 산출물이 없으면 얻은 것으로 치지 않는다.

| # | 경험 | 끝났을 때 말할 수 있는 것 | 증거 산출물 | 우선순위 |
|---|---|---|---|---|
| E1 | **측정 기반 성능 개선** | "기준선을 재고, 지표로 병목을 찾고, 개선 후 다시 재서 효과를 확인했다"를 사례 3개 이상으로 | `docs/perf/` 측정 기록, 개선 PR과 전후 그래프 | 최상 |
| E2 | **데이터 모델링과 객체지향 설계** | ERD의 주요 결정, 패키지 구조, 예외 처리, 스키마 관리 방식을 왜 그렇게 정했는지. 서비스에 몰린 로직을 도메인 객체로 옮기며 무엇이 나아졌는지 | ERD 문서, 설계 결정 기록, 리팩터링 전후 PR | 상 |
| E3 | **동시성·정합성과 비동기 처리** | 동시 요청에서 데이터가 깨지는 상황을 재현하고 해결책을 비교해 고른 이유. 어떤 작업을 왜 비동기로 분리했고, 그때 생기는 문제(트랜잭션 경계, 실패 처리)를 어떻게 다뤘는지 | 동시성 테스트 코드, 비교 기록, 비동기 처리 PR | 상 |
| E4 | **배포·운영과 장애 대응** | 코드가 머지되고 운영 서버에 올라가기까지의 흐름, 서버 상태를 어떤 지표로 보는지, 장애를 어떻게 알아채고 추적하고 기록했는지 | CI/CD 설정, 대시보드와 알람, 장애 회고 문서 | 중 |
| E7 | **인증과 인가** | 토큰 인증 흐름, 재발급, 권한별 접근 제어를 필터 체인 수준에서 설명 | 시큐리티 설정 PR, 인증 흐름 그림 | 중 |
| E5 | **깃허브 기반 개발 과정** | 이슈에서 릴리즈까지 한 사이클을 규칙 있게 운영한 경험 | 이슈·PR·릴리즈 이력, 템플릿 | 중 |
| E6 | **AI 도구를 활용한 개발 방식** | AI가 쓴 코드를 어떻게 검증하고 이해했는지, 어디까지 맡기고 어디서 판단했는지 | `docs/learning/` 노트, 회고 | 하 |

**우선순위의 의미**: 일정이 밀리면 아래부터 줄인다. E1은 줄이지 않는다.

### 1.3 하지 않는 것

- 마이크로서비스 분리: 혼자 운영하는 규모에서 얻는 것보다 부담이 크다
- 실제 결제 대행사 연동: 결제 정합성 문제는 모의 결제로 충분히 다룬다
- 기능 완성도 경쟁: 기능 수는 평가 대상이 아니다. 성능·정합성 실험의 재료로만 만든다
- 프론트엔드 품질: 시연용 최소 화면만. AI 생성이며 평가 범위 밖
- 외부 메시지 브로커(카프카 등), 배치, 서킷 브레이커: v1.0.0 이후 과제로 남긴다. 애플리케이션 내부의 비동기 처리는 11주차에 다룬다
- 스테이징 환경 별도 구축: 비용 문제로 로컬과 운영 두 환경만 둔다

## 2. 서비스 개요

### 2.1 무엇을 만드는가
작품과 회차를 등록하고, 독자가 회차를 열람하고, 댓글과 좋아요를 남기고, 유료 회차는 쿠키로 구매하는 웹툰 플랫폼.

### 2.2 사용자 역할
| 역할 | 할 수 있는 일 |
|---|---|
| 독자 | 작품 목록·회차 열람, 댓글, 좋아요, 쿠키 충전(모의), 유료 회차 구매 |
| 작가 | 작품 등록, 회차 업로드(이미지 여러 장), 공개 시각 예약 |
| 관리자 | 이번 범위에서 제외 |

### 2.3 이 서비스를 고른 이유
웹툰은 기술 과제를 자연스럽게 품고 있다.
- 대부분이 읽기 요청이고, 인기작 소수에 몰린다 → 캐시와 CDN
- 정해진 시각에 신작이 공개된다 → 순간 몰림
- 조회수·좋아요가 동시에 갱신된다 → 쓰기 경합
- 유료 회차 구매가 있다 → 돈이 걸린 정합성
- 회차마다 이미지가 많다 → 대용량 파일 분리

## 3. 핵심 기술 과제

각 과제는 E1, E3의 재료다. "재현 → 측정 → 개선 → 재측정" 순서를 지킨다.

### 과제 1. 회차 목록·작품 목록 조회 성능
- **상황**: 회차 50만 건, 작품 1만 건 규모에서 목록 조회
- **예상 문제**: 인덱스 누락, N+1 쿼리, 뒤쪽 페이지로 갈수록 느려지는 오프셋 방식
- **검증 방법**: 부하 테스트로 응답 시간 분포와 처리량 측정, 느린 쿼리 로그와 실행 계획 확인
- **결과물**: 개선 전후 수치, 실행 계획 비교

### 과제 2. 회차 열람 캐시
- **상황**: 인기 회차에 읽기 요청이 몰림
- **예상 문제**: 매 요청이 DB까지 감
- **검증 방법**: 캐시 적중률, DB 쿼리 수, 응답 시간
- **함께 다룰 것**: 회차 수정 시 캐시 무효화, 캐시 서버가 죽었을 때의 동작

### 과제 3. 신작 공개 순간의 몰림
- **상황**: 공개 시각에 동시 접속 급증, 캐시는 비어 있음
- **예상 문제**: 캐시 스탬피드로 DB에 요청 폭주
- **검증 방법**: 공개 시각을 재현하는 부하 시나리오로 DB 부하와 에러율 측정
- **해결 후보**: 공개 전 캐시 미리 채우기, 같은 키 요청 합치기, 만료 시각 분산

### 과제 4. 조회수·좋아요 동시 갱신
- **상황**: 같은 회차에 동시에 조회와 좋아요가 발생
- **예상 문제**: 갱신 누락, 행 잠금 경합
- **검증 방법**: 동시 요청 테스트 후 최종 값 검증, 처리량 비교
- **해결 후보**: DB 원자적 갱신, Redis에 모았다가 일괄 반영

### 과제 5. 유료 회차 구매 정합성
- **상황**: 같은 사용자가 동시에 여러 번 구매 요청 (더블 클릭, 재시도)
- **예상 문제**: 쿠키 중복 차감, 잔액 음수
- **검증 방법**: 동시성 테스트로 잔액과 구매 기록 일치 여부 확인
- **해결 후보**: 비관적 잠금, 낙관적 잠금, 멱등키 → 비교 후 선택

### 과제 6. 요청 흐름에서 부가 작업 분리
- **상황**: 회차 열람 시 조회수 기록, 신작 공개 시 구독자 알림처럼 응답에 꼭 필요하지 않은 작업이 요청 안에서 함께 처리됨
- **예상 문제**: 응답 지연, 부가 작업 실패가 본 작업까지 실패시킴
- **검증 방법**: 분리 전후 응답 시간 비교, 부가 작업 실패를 일부러 일으켜 본 작업 영향 확인
- **함께 다룰 것**: 트랜잭션 커밋 후에만 실행되는 이벤트, 비동기 스레드 풀 크기와 대기열이 가득 찼을 때의 동작, 실패한 작업 재처리

## 5. 비기능 요구사항

### 5.1 성능 목표
**기준선을 측정하기 전에는 목표 수치를 정하지 않는다.** 근거 없는 목표는 의미가 없다. 7주차 기준선 측정 후 아래 표를 채운다.

| 시나리오 | 데이터 규모 | 동시 사용자 | 기준선 | 목표 | 최종 |
|---|---|---|---|---|---|
| 회차 목록 조회 | 회차 50만 | 미정 | | | |
| 회차 열람 | 〃 | 미정 | | | |
| 신작 공개 순간 | 〃 | 미정 | | | |
| 댓글 목록 | 댓글 수천만 | 미정 | | | |

지표: 응답 시간(중앙값, 상위 5%, 상위 1%), 초당 처리량, 에러율

### 5.2 측정 환경 원칙
- 부하 생성기와 서버는 다른 기기에서 실행한다
- 측정 조건(장비 사양, 데이터 규모, 시나리오, 측정 시간)을 매번 기록한다
- 같은 조건에서 최소 3회 측정한다

### 5.3 테스트 데이터 생성 원칙

**실제 웹툰 데이터와 이미지는 사용하지 않는다.** 공식 공개 API가 없고, 이미지 재배포는 저작권 문제가 있으며, 실제 데이터는 목표 규모에 한참 못 미친다. 모든 데이터는 생성한다.

핵심은 데이터가 진짜인지가 아니라 **분포가 현실적인지**다. 고르게 분포된 무작위 데이터는 측정 결과를 왜곡한다.

| 대상 | 분포 | 이유 |
|---|---|---|
| 작품 인기도 (조회 대상 선택) | 소수에 몰리는 멱법칙 분포 (지프 분포 등) | 고른 분포면 캐시 적중률이 비현실적으로 낮게 나온다 |
| 작품당 회차 수 | 3화 신작부터 500화 이상 장기 연재작까지 섞음 | 회차 목록 뒤쪽 페이지 성능 문제를 드러내기 위해 |
| 회차당 댓글 수 | 인기 회차에 수만 개, 대부분은 소수 | 댓글 목록 조회의 최악 조건을 재현하기 위해 |
| 공개 시각 | 요일별로, 같은 시각에 몰리게 | 과제 3의 순간 몰림 재현 |
| 회원 활동 | 일부 회원이 좋아요·댓글 대부분을 차지 | 회원 기준 조회의 쏠림 재현 |

**생성 방식**
- 생성 스크립트는 `infra/data/`에 두고, 분포 설정값(작품 수, 쏠림 정도 등)을 인자로 받게 한다
- 같은 시드를 쓰면 같은 데이터가 나오게 해서 측정 간 비교가 가능하게 한다
- 대량 삽입은 애플리케이션을 거치지 않고 DB에 직접 일괄 삽입한다
- 분포 설계 근거와 생성 결과 요약(테이블별 건수, 상위 1% 작품이 차지하는 비중 등)을 `docs/perf/`에 기록한다

**시연용 데이터와 이미지**
- 작품 제목·줄거리는 AI로 생성해 수백 개만 둔다
- 이미지는 실제 웹툰과 비슷한 크기·용량의 자체 제작 이미지 몇 장을 키만 바꿔 재사용한다. 저장소와 CDN 테스트에는 이것으로 충분하다

## 6. 기술 스택과 선택 이유

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어·프레임워크 | 자바 21, 스프링 부트 4.x | 주력 기술. 최신 메이저 버전의 변경점(모듈화된 스타터, 잭슨 3)도 경험 |
| DB | MySQL 8.4 | 현재 장기 지원 버전. 실행 계획 분석과 인덱스 학습 자료가 풍부 |
| 스키마 관리 | 플라이웨이 | 인덱스 추가 이력을 버전으로 남겨 성능 개선 근거로 활용 |
| 캐시·카운터 | Redis 7 | 과제 2~4에 공통으로 사용 |
| 파일 저장 | 객체 저장소 + CDN | 이미지를 애플리케이션 서버에서 분리 |
| 테스트 | JUnit 5, 테스트 컨테이너 | 실제 MySQL 환경에서 쿼리 검증 |
| 부하 테스트 | k6 | 시나리오를 코드로 관리, 저장소에 함께 보관 |
| 인증·인가 | 스프링 시큐리티, 토큰 인증 | 필터 체인 구조를 직접 다루며 이해 |
| 관측 | 프로메테우스, 그라파나, 디스코드 알람 | 스프링 지표 연동이 쉬움. 알람은 개인이 바로 받을 수 있는 채널로 |
| 배포 | 도커, 깃허브 액션, AWS | 프리 티어 범위 안에서 운영 |

세부 결정은 `docs/adr/`에 남긴다.

### 7.1 학습 주제 대응

백엔드 핵심 주제를 **교재식으로 따라 하지 않고, 이 서비스의 문제에 적용**한다. 각 주제마다 "이 프로젝트에서 답해야 할 질문"이 있다.

| 학습 주제 | 이 프로젝트에서 적용할 것 | 답해야 할 질문 | 산출물 |
|---|---|---|---|
| 스프링 튜토리얼 | 프로젝트 생성, 설정 분리, 공통 응답·예외 처리, 로컬 환경 | 스프링 컨테이너가 빈을 언제 만들고 주입하는가 | v0.0.1, 설계 결정 기록 |
| DB 접근 기술 | JPA 엔티티 매핑, 연관관계, 페치 조인, 플라이웨이 | 이 조회에서 쿼리가 몇 번 나가는가, 왜 그런가 | 쿼리 로그가 담긴 PR |
| MVC 아키텍처 | 컨트롤러·서비스·저장소 책임 분리, 요청·응답 객체 | 이 로직은 어느 계층에 있어야 하는가 | 패키지 구조 설계 결정 기록 |
| 자바와 객체지향 | 4주차 말 리팩터링: 서비스에 몰린 로직을 엔티티와 값 객체로 이동 (예: 쿠키 금액, 회차 공개 여부 판단) | 이 객체는 스스로 무엇을 책임지는가 | 리팩터링 전후 비교 PR |
| 보안과 스프링 시큐리티 | 임시 인증을 토큰 인증으로 교체, 재발급, 작가·본인만 가능한 작업의 인가, 401·403 응답 형식 통일 | 요청이 필터 체인을 어떻게 통과하는가 | 인증 흐름 그림, 시큐리티 PR |
| 배포 | 도커 이미지, 깃허브 액션 자동 배포, 환경 변수·시크릿, 롤백 | 지금 운영 중인 버전이 무엇이고 어떻게 되돌리는가 | 배포 파이프라인, 롤백 연습 기록 |
| 모니터링과 로깅 | 요청 식별자 로그, 구조화 로그, 대시보드, 에러율·응답 시간 알람 | 장애가 나면 무엇을 보고 알아채는가 | 대시보드, 알람 규칙 |
| 최적화와 캐싱 | 과제 1~3 | 병목을 어떻게 찾았고, 개선 효과는 얼마인가 | `docs/perf/` 기록 |
| 비동기 처리 | 과제 4, 6: 조회수 기록과 알림을 커밋 후 이벤트와 비동기 처리로 분리 | 비동기로 바꾸면 무엇을 잃는가 | 비동기 처리 PR, 설계 결정 기록 |

### 7.2 실무 한 사이클

기능을 만드는 것에서 끝내지 않고, 실무의 흐름을 한 바퀴 돈다.

```
요구사항 → 설계 → 구현 → 리뷰 → 배포 → 관측 → 장애 대응 → 회고
```

| 단계 | 이 프로젝트에서 하는 것 |
|---|---|
| 요구사항 | 이슈를 사용자 관점 문장과 완료 조건으로 작성 |
| 설계 | 큰 작업은 구현 전에 설계 결정 기록이나 이슈 본문에 설계를 먼저 적음 |
| 구현 | 개념 단계 → 적용 단계 (CLAUDE.md 학습 방식) |
| 리뷰 | PR 템플릿의 체크리스트로 셀프 리뷰, 가능하면 리뷰어 1명 |
| 배포 | 태그 푸시로 자동 배포, 운영 배포 승인 단계 |
| 관측 | 대시보드와 알람으로 배포 후 상태 확인 |
| 장애 대응 | 12주차에 일부러 장애를 일으켜 알람 수신 → 로그 추적 → 조치 → 롤백까지 진행 |
| 회고 | 장애 회고 문서(`docs/postmortem/`)와 프로젝트 회고 |

- [ ] 이슈와 연결된 PR이 있다
- [ ] 테스트가 있고 CI를 통과한다
- [ ] 설계 판단이 있었다면 설계 결정 기록이 있다

- [ ] 이 코드를 남에게 설명할 수 있다

### 8.3 면접 준비 확인
끝났을 때 아래 질문에 막힘없이 답할 수 있어야 한다.
- 가장 효과가 컸던 성능 개선은 무엇이고, 병목을 어떻게 찾았나?
- 캐시를 도입하면서 생긴 새 문제는 무엇이었나?
- 쿠키 중복 차감은 어떤 방법으로 막았고, 다른 방법 대신 그걸 고른 이유는?
- 응답 형식과 예외 처리 구조를 왜 그렇게 설계했나?
- AI가 짠 코드를 어떻게 검증했나?
- 로그인 요청이 들어와서 토큰이 발급되기까지 시큐리티 내부에서 무슨 일이 일어나나?
- 조회수 기록을 비동기로 바꾸면서 생긴 문제는 무엇이었나?
- 운영 중 에러율이 치솟으면 무엇부터 확인하나?
